# SDD 规格驱动开发

目前有github 的Spec kit、Openspec、Kiro等

本质是都是Skill

VibeCoding + SDD = Harness 工程具像化

## 核心思想

先让 AI 理解需求、明确设计、拆分任务，再让 AI 编写代码，最后通过测试和验证形成闭环。

Specify 管需求，Plan 管设计，Tasks 管执行，Implement 管实现，Converge 管交付；Clarify、Analyze、Checklist 负责在关键节点把质量守住。



## 开发中执行顺序

**第一阶段：基于PRD生成官方需求 Sepcify**

*第二阶段：需求澄清补全  **Clarify*** 

​	质量门禁一：原则：有歧义先澄清，不要让AI自己猜业务规则

*第三阶段：要生成质量清单  **checklist*** 

​	质量门禁二：检查需求规格本身是否完整明确、可验证

**第四阶段：生成技术实现方案  Plan**

**第五阶段：拆解可执行开发任务 Tasks**

​	生成tasks.md，任务最好具备明确的输入、输出、文件范围和验收范围

*第六阶段：一致性检查 **Analyze***

​	质量门禁三：让AI对照Spec.md、Plan.md、Tasks.md检查：

​		需求是否全部覆盖、是否有需求没有对应任务、设计是否与业务规则冲突、任务是否存在遗漏或重复、		是否违反项目架构约束				

**第七阶段：生成代码 Implement**

​	AI根据tasks.md 逐项修改代码，运行测试，并更新任务完成状态。推荐不要一次性让AI完成整个复杂功能，而是按阶段开发检查

**第八阶段：项目全局自检校准 Converge**（人工+AI）

​	执行测试 --> 发现问题 --> 修复代码 --> 重新执行测试 --> 对照 Spec验收 -->代码Review --> 交付



## 案例

需求是算路成功15秒误操作自动进入导航。

### 第一步：基于PRD生成官方需求 Sepcify

- 首次算路成功，启动15秒倒计时。

- 倒计时结束后自动进入导航。

- 用户触摸页面立即取消倒计时。

- 切换路线时取消倒计时。

- 算路失败不启动倒计时。

- Fragment 销毁后不允许继续触发导航。

### 第二步：需求澄清

使用

```
/speckit.clarify
```

这是第一个质量门禁，用来发现需求中没有说清楚的地方。

例如 AI 应当提出：

- 用户触摸后，倒计时是否允许再次启动？
- 重新算路成功后是否重新倒计时？
- App 进入后台，倒计时继续还是暂停？
- 路线列表切换后是否需要恢复默认状态？

原则：有歧义先澄清，不要让 AI 自己猜业务规则。

### 第三步：技术方案

```
/speckit.plan
```

核心问题：怎么实现？

这时才引入技术约束

```
项目使用 Kotlin/Java、MVI 架构。

RouteResultFragment 负责 UI 展示。
RouteResultDispatcher 负责 Intent 分发。
RouteResultUseCase 负责业务逻辑。
RouteStates 管理倒计时 UI 状态。

要求复用现有代码，不能破坏路线刷新逻辑。
```

### 第四步：任务拆分

```
/speckit.tasks
```

将技术方案拆成可以独立执行、验证的小任务，生成 `tasks.md`。

```
T001 定义倒计时相关 UiState
T002 新增 StartCountdown Intent
T003 新增 CancelCountdown Intent
T004 在 Dispatcher 中处理倒计时
T005 Fragment 绑定倒计时 UI
T006 处理用户触摸事件
T007 处理页面销毁及资源释放
T008 编写倒计时单元测试
T009 执行回归测试
```

### 第五步：一致性检查

```
/speckit.analyze
```

例如，需求写了“进入后台取消倒计时”，但任务列表没有任何生命周期处理，Analyze 就应该指出这个缺口。

### 第六步：编码实现

AI 根据 `tasks.md` 逐项修改代码，运行测试，并更新任务完成状态

### 第七步：最终收敛



## 什么时候需要执行全部流程？

不是所有需求都值得走完整流程。

| 需求类型           | 推荐流程                                  |
| ------------------ | ----------------------------------------- |
| 修改按钮文案、颜色 | 直接实现 + 验证                           |
| 小型 Bug 修复      | Specify → Implement → 验证                |
| 普通业务功能       | Specify → Plan → Tasks → Implement → 验证 |
| 跨模块复杂需求     | 全流程，加入 Clarify、Checklist、Analyze  |
| 重大架构调整       | 全流程 + 人工技术评审 + 回归测试          |

采用一个原则：AI 负责生成规格、设计、任务和代码；开发者负责确认业务决策、审查架构、验证结果。
